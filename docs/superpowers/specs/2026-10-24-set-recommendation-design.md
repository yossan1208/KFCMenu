# セットのおすすめ表示 設計書

- 作成: 2026-10-24
- ステータス: ユーザー確認待ち
- 前提: `docs/superpowers/specs/2026-09-05-kfc-menu-optimizer-design.md`（以下「元の設計書」）。この設計書の内容が、元の設計書の「画面」「スコープ」のうち余剰の上限に関する部分を置き換える。

## 背景・目的

今の計算は「支払う金額が一番安い買い方」だけを出す。セットは単品で揃えるより必ず安いが、頼んでいない品物（サイド・ドリンク）が付いてくるため、余剰の上限が0だと使われず、ほとんどの結果が単品の組み合わせになる。ユーザーはセットを多く使った、お得な買い方を見たい。

例（menu.jsonの現在の価格）:
- チキン2本: 最安は 単×2 = 660円。2セット 890円 なら +230円 でポテトとドリンク（単品なら560円分）が付く
- バーガー2・ドリンクM2: 最安は単品 1,460円。セット×2 なら 1,380円 で、最安より80円安くポテトも付く

## ユーザーが決めたこと

- 最安はそのまま表示し、その下にセットを使った「おすすめ」を並べる
- おすすめは「単品の数が少ない順、同じなら安い順」に最大3つ
- 最安の1.5倍を超えるおすすめは出さない
- 「余剰の上限」の入力欄はなくす。入力は「必要数」だけ
- 実装方法は案1: 計算ロジック（KfcMenu.Core）に、おすすめを探す部品を新しく作る。今の最安探索（CheapestComboFinder）は変えない

## 用語

- **品数**: 購入選択肢1つに入っている品物の数。`includes` の個数の合計 + 選べる枠の `count` の合計。例: 4パック = チキン4 + サイド枠2 = 6、単 = 1
- **セット**: 品数が2以上の購入選択肢（パックも含む）
- **単品**: 品数が1の購入選択肢（単、ポテs、S など）
- **単品価格**: 商品ごとに、「選べる枠がなく、`includes` がその商品1個だけ」の購入選択肢のうち最も安い価格。現在のmenu.jsonでは16商品すべてにある
- **単品換算**: ある買い方の中身を、すべて単品価格で買った場合の合計
- **お得額**: 単品換算 − 実際の合計金額

## 振る舞い

### 入力

- 商品ごとの「必要数」（0〜99）。範囲外ならエラーメッセージを表示して計算しない（今と同じ）
- 「余剰の上限」の列は画面から削除する。menu.jsonの `MaxSurplus` とモデルの `Product.MaxSurplus` は残すが、画面では使わない

### 最安

- 頼んだものだけで、全商品の合計個数が必要数とちょうど一致する買い方のうち、最も安いもの
- 実装: 全商品の `MaxSurplus` を0にして、今の `CheapestComboFinder.FindCheapest` を呼ぶ
- 表示は今と同じ（「4パック × 1（サイド: クリスピー, クリスピー）」の形式と合計金額）

### おすすめ（SetRecommender）

候補は次の条件をすべて満たす買い方:

1. 各商品の合計個数が必要数**以上**（頼んでいないものや、必要数を超える分が付いてもよい）
2. セットを1つ以上含む
3. 無駄がない: どの購入選択肢を1つ取り除いても、どれかの商品が必要数を下回る
4. 合計金額が最安の1.5倍以下（小数点以下切り捨て）。最安が見つからない場合はこの条件なし
5. 最安と同じ組み合わせではない（購入選択肢ごとの個数が同じなら同じとみなす）

並べ方と件数:
- 単品の個数（購入数の合計）が少ない順、同じなら合計金額が安い順。最大3つ
- 購入選択肢ごとの個数が同じ候補は1つにまとめる（選べる枠の選び方違いは出さない）

選べる枠の扱い:
- 枠の候補のうち、必要数が1以上の商品は、その商品として必要数に数える
- それ以外は「お好きなもの」として扱い、どの商品の必要数にも数えない。表示は「お好きな{枠のlabel}」（例: お好きなサイド）
- 「お好きなもの」の単品換算は、その枠の候補の単品価格の最小値

おすすめごとに表示する内容:
- 中身: 「8パック × 1（サイド: お好きなサイド ×4）」のように、購入選択肢ごとに個数と枠の中身
- 合計金額
- 最安との差: 高ければ「+350円」、安ければ「80円安い」、同額なら「最安と同額」
- お得額: 「単品より810円お得」。お得額が0以下なら表示しない
- 追加で付くもの: 必要数を超える分（例: チキン +2）と、お好きなもの（例: お好きなサイド ×4）

どの候補も条件を満たさない場合は「セットを使ったおすすめはありません」と表示する。必要数がすべて0の場合もこの表示になる（最安は0円、上限も0円のため）。

### 例（menu.jsonの現在の価格。値は実装計画で自動テストの期待値として確定する）

| 注文 | 最安 | おすすめ（順に） |
|---|---|---|
| チキン8 | 単×8 2,640円 | 8パック 2,990円 / 4パック×2 3,180円 / 2セット + 3セット×2 3,270円 |
| チキン2 | 単×2 660円 | 2セット 890円 / チキビス + 単 880円 / キッズチキン + 単 920円（1.5倍上限990円のため、チキビス×2 1,100円は出ない） |
| チキン1・ポテトS1・ビスケット1 | 単品3つ 910円 | チキビス 550円 ほか（1.5倍上限1,365円のため、4パック 1,590円は出ない） |
| バーガー2・ドリンクM2 | 単品 1,460円 | セット×2 1,380円 ほか |

## 探索方法

- 必要数が1以上の商品だけを対象にする
- 購入選択肢を、その注文向けに展開する: 選べる枠の各席を「必要数が1以上の候補商品」または「お好きなもの」から選ぶ。必要数が1以上の商品を1つも含まない展開結果は使わない
- 状態は「各商品の合計個数（必要数で頭打ち）」。まだ必要数に届いていない最初の商品を選び、その商品を含む展開結果を1つ足して次の状態へ進む
- 状態ごとに「そこから必要数を満たすまでの買い方」の上位40件を、（単品の個数, 金額）の順で保持する（メモ化）。同じ組み合わせは安い方だけ残す
- 最初の状態の上位40件から、条件2〜5で絞り込み、上位3件を返す

既知の制限: 状態ごとに上位40件しか残さないため、条件3〜5で多くの候補が落ちる注文では、本来の上位3件を見落とす可能性がある。

## 性能

- 試作（Python）では、通常の注文は数ms、チキン30・ポテト10・ドリンク10・ビスケット4 の大量注文で約12秒（Python）だった
- 実装後にPC（.NET）とブラウザ（WASM）の両方で計測し、結果を元の設計書の「性能」節に追記する
- 目標: 通常の注文（家族分程度）はブラウザで1秒以内。大量注文で目標を超える場合は既知の制限として記録する（「計算中...」表示は今と同じく出す）
