# セットのおすすめ表示 設計書

- 作成: 2026-10-24
- ステータス: 承認済み・実装済み
- 前提: `docs/superpowers/specs/2026-09-05-kfc-menu-optimizer-design.md`（以下「元の設計書」）。この設計書の内容が、元の設計書の「画面」「スコープ」のうち余剰の上限に関する部分を置き換える。

## 背景・目的

今の計算は「支払う金額が一番安い買い方」だけを出す。セットは単品で揃えるより必ず安いが、頼んでいない品物（サイド・ドリンク）が付いてくるため、余剰の上限が0だと使われず、ほとんどの結果が単品の組み合わせになる。ユーザーはセットを多く使った、お得な買い方を見たい。

例（menu.jsonの現在の価格）:
- チキン2本: 最安は 単×2 = 660円。2セット 890円 なら +230円 でポテトとドリンク（単品なら560円分）が付く
- バーガー2・ドリンクM2: 最安は単品 1,460円。セット×2 なら 1,380円 で、最安より80円安くポテトも付く

## ユーザーが決めたこと

- 最安はそのまま表示し、その下にセットを使った「おすすめ」を並べる
- おすすめは「単品の数が少ない順、同じなら安い順」に最大3つ
- 最安の1.5倍を超えるおすすめは出さない
- 「余剰の上限」の入力欄はなくす。入力は「必要数」だけ
- 実装方法は案1: 計算ロジック（KfcMenu.Core）に、おすすめを探す部品を新しく作る。今の最安探索（CheapestComboFinder）は変えない

## 用語

- **品数**: 購入選択肢1つに入っている品物の数。`includes` の個数の合計 + 選べる枠の `count` の合計。例: 4パック = チキン4 + サイド枠2 = 6、単 = 1
- **セット**: 品数が2以上の購入選択肢（パックも含む）
- **単品**: 品数が1の購入選択肢（単、ポテs、S など）
- **単品価格**: 商品ごとに、「選べる枠がなく、`includes` がその商品1個だけ」の購入選択肢のうち最も安い価格。現在のmenu.jsonでは16商品すべてにある
- **単品換算**: ある買い方の中身を、すべて単品価格で買った場合の合計
- **お得額**: 単品換算 − 実際の合計金額

## 振る舞い

### 入力

- 商品ごとの「必要数」（0〜99）。範囲外ならエラーメッセージを表示して計算しない（今と同じ）
- 「余剰の上限」の列は画面から削除する。menu.jsonの `MaxSurplus` とモデルの `Product.MaxSurplus` は残すが、画面では使わない

### 最安

- 頼んだものだけで、全商品の合計個数が必要数とちょうど一致する買い方のうち、最も安いもの
- 実装: 全商品の `MaxSurplus` を0にして、今の `CheapestComboFinder.FindCheapest` を呼ぶ
- 表示は今と同じ（「4パック × 1（サイド: クリスピー, クリスピー）」の形式と合計金額）

### おすすめ（SetRecommender）

候補は次の条件をすべて満たす買い方:

1. 各商品の合計個数が必要数**以上**（頼んでいないものや、必要数を超える分が付いてもよい）
2. セットを1つ以上含む
3. 無駄がない: どの購入選択肢を1つ取り除いても、残りの選べる枠の選び方をどう変えても、どれかの商品が必要数を下回る（例: ポテトS1・ドリンクS1・ナゲット1 で「S + キッズナゲット（お好きなドリンク）」は、ドリンクの枠でSを選べばSが要らないので無駄がある）
4. 合計金額が最安の1.5倍以下（小数点以下切り捨て）。最安が見つからない場合はこの条件なし
5. 最安と同じ組み合わせではない（購入選択肢ごとの個数が同じなら同じとみなす）

並べ方と件数:
- 単品の個数（購入数の合計）が少ない順、同じなら合計金額が安い順。最大3つ
- 購入選択肢ごとの個数が同じ候補は1つにまとめる（選べる枠の選び方違いは出さない）

選べる枠の扱い:
- 枠の候補のうち、必要数が1以上の商品は、その商品として必要数に数える
- それ以外は「お好きなもの」として扱い、どの商品の必要数にも数えない。表示は「お好きな{枠のlabel}」（例: お好きなサイド）
- 「お好きなもの」の単品換算は、その枠の候補の単品価格の最小値

おすすめごとに表示する内容:
- 中身: 「8パック × 1（サイド: お好きなサイド ×4）」のように、購入選択肢ごとに個数と枠の中身
- 合計金額
- 最安との差: 高ければ「+350円」、安ければ「80円安い」、同額なら「最安と同額」
- お得額: 「単品より810円お得」。お得額が0以下なら表示しない
- 追加で付くもの: 必要数を超える分（例: チキン +2）と、お好きなもの（例: お好きなサイド ×4）

どの候補も条件を満たさない場合は「セットを使ったおすすめはありません」と表示する。必要数がすべて0の場合もこの表示になる（最安は0円、上限も0円のため）。

### 例（menu.jsonの現在の価格。値は実装計画で自動テストの期待値として確定する）

| 注文 | 最安 | おすすめ（順に） |
|---|---|---|
| チキン8 | 単×8 2,640円 | 8パック 2,990円 / 4パック×2 3,180円 / 2セット + 3セット×2 3,270円 |
| チキン2 | 単×2 660円 | 2セット 890円 / チキビス + 単 880円 / キッズチキン + 単 920円（1.5倍上限990円のため、チキビス×2 1,100円は出ない） |
| チキン1・ポテトS1・ビスケット1 | 単品3つ 910円 | チキビス 550円 ほか（1.5倍上限1,365円のため、4パック 1,590円は出ない） |
| バーガー2・ドリンクM2 | 単品 1,460円 | セット×2 1,380円 ほか |

## 探索方法

- 必要数が1以上の商品だけを対象にする
- 購入選択肢を、その注文向けに展開する: 選べる枠の各席を「必要数が1以上の候補商品」または「お好きなもの」から選ぶ。必要数が1以上の商品を1つも含まない展開結果は使わない
- 状態は「各商品の合計個数（必要数で頭打ち）」。まだ必要数に届いていない商品のうち、それを含む展開結果が最も少ない商品を選び（どれを選んでも漏れなく探せる。少ない商品からの方が分岐が減って速い）、その商品を含む展開結果を1つ足して次の状態へ進む
- 状態ごとに「そこから必要数を満たすまでの買い方」を2通りの上位で保持する（メモ化）: （単品の個数, 金額）順の上位40件と、金額順の上位40件。同じ組み合わせ（展開結果の多重集合）は1つだけ残す
  - 前者だけだと、単品は少ないが高い買い方で埋まり、親で品物を足すと1.5倍上限を超えてしまう。上限内に収まる安い買い方はすでに切り捨てられていて、「おすすめはありません」になる注文が多かった（ドリンクM4・ドリンクS2・ナゲット1 など）。後者がそれを残す
- それぞれの上位40件は、足す展開結果ごとの「次の状態の同じ順の上位40件」（どれも並び順どおり）を先頭から突き合わせて（k-way merge）作る。同順位は足す展開結果の順で決める。買い方は「最後に足したもの＋それ以前の買い方」の連結リストで持ち、組み合わせの重複は順番によらない64bitハッシュで除く
- 状態まで来るのにかかった金額の下限を見積もり、「上限 − 下限」を超える買い方はその状態で残さない（どう組み合わせても上限を超えるので、捨てても漏れない）。下限は Σ 商品kの個数 × 「商品kを含む展開結果の、価格 ÷ 含まれる頼んだ商品の個数の合計」の最小値（どの展開結果も頼んだ商品1個あたりこれより安くは配れない）。上限を超えるだけの買い方で上位40件が埋まるのを防ぐ
- 最初の状態の2つの上位を合わせ（同じ組み合わせは1つ）、（単品の個数, 金額）順に並べ直して、条件2〜5で絞り込み、上位3件を返す
- 条件3は、購入選択肢ごとの個数だけで決まる（席の選び方は変えてよいため）。1つ取り除いた残りについて、includes で足りない分を、選べる枠の席（枠の候補にある頼んだ商品なら何でも選べる）で埋められるかを最大流で調べる。重複不可の枠は1個につき各商品1席まで。表示する枠の中身は、その買い方自身の選び方

既知の制限: 状態ごとに2通りの上位40件ずつしか残さないため、本来の上位3件を見落とす注文はまだある。2026-10-24の計測では、商品1〜4種類・各1〜3個のランダムな注文200件のうち、総当たり（試作スクリプトを条件3の新しい定義に直したもの）と上位3件の（単品の個数, 金額）が違ったのは2件で、どちらも件数は3件出ていた（もっと単品の多い・高い候補で埋まった）。「セット1つ + 残りを単品」で条件を満たす買い方がある注文で「おすすめはありません」になったものは、各300件のランダムな注文（各商品の個数の上限 2・4・6・10）で0件。

## 性能

- 試作（Python）では、通常の注文は数ms、チキン30・ポテト10・ドリンク10・ビスケット4 の大量注文で約12秒（Python）だった
- 実装後にPC（.NET）とブラウザ（WASM）の両方で計測し、結果をこの設計書のこの節に記録する
- 目標: 通常の注文（家族分程度）はブラウザで1秒以内。大量注文で目標を超える場合は既知の制限として記録する（「計算中...」表示は今と同じく出す）

| 家族4人（チキン6・ポテトS2・ドリンクS2・バーガー1・ビスケット2） | 29ms |
| G: チキン30・ポテトS10・ドリンクS10・ビスケット4 | 393ms |
| H: チキン12・ポテトS6・ドリンクS6・ビスケット4・クリスピー3・チョコパイ2・コールスロー2・バーガー2 | 1050ms |

2通りの上位・金額の下限による絞り込み・条件3の変更の後（2026-10-24、同じ環境）。ブラウザの「合計」は「計算」を押してから結果が表示されるまで（20msごとの確認なので20ms程度の誤差を含む）、内訳は計測用に一時的に Stopwatch を入れた別のビルドでの値（最安 / おすすめ、別の回の計測）。PCは .NET Release で5回の中央値:

## テスト

- `SetRecommenderTests`: 本物のmenu.jsonで、上の例の注文について、おすすめの組み合わせ・順番・金額・お得額・追加で付くもの・件数を確認する。期待値は別の総当たり計算（試作スクリプト）と照合して実装計画で確定する
- 単体の小さなメニューで、条件3（無駄がない）、条件4（1.5倍上限）、条件5（最安と同じものを除く）、セットがない場合に空になることを確認する
- テスト側の検査（`RecommendationChecker`、SetRecommender とは別の書き方で条件1〜5を確かめる）で、返ったおすすめがすべて条件を満たすことを確認する。以前「おすすめはありません」になっていた注文、選べる枠で単品が要らなくなる注文、固定の乱数で作った200件の小さな注文（「セット1つ + 残りを単品」で条件を満たす買い方が m 通りあれば少なくとも min(3, m) 件出ること）を含む
- 既存の18件のテストはそのまま通ること
- 画面はブラウザで確認する（公開用ビルドをサブパスで配信し、ヘッドレスChromeで確認する今の手順）
